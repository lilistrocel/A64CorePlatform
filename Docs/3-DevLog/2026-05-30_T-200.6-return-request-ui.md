## 3. Bugs/Issues Discovered

### B1: No from-delivery backend endpoint for RR (RESOLVED — design decision)
The backend `return_requests` service has no `/from-delivery/:dnDocEntry` endpoint, unlike
`ar-invoices` which has a dedicated one. The frontend `createReturnRequestFromDelivery` function
delegates to the standard `createReturnRequest`, with the Delivery's docEntry/docNumber captured
in `baseDocRef`. The from-delivery mode in the form pre-fills by fetching the Delivery via
`useDelivery` and copying its lines client-side.

### B2: Reason filter not supported by list endpoint (RESOLVED — client-side filter)
The `/return-requests` list endpoint accepts `status`, `customer_id`, `date_from`, `date_to` but
NOT `reason`. The reason chip filter in `ReturnRequestsPage` applies a `.filter()` on `data.data`
after the server response.

### B3: Broken docstring structure from Edit tool insertion (RESOLVED — full file rewrite)
When `model_config = _RESPONSE_CONFIG` was inserted into `ReturnRequestLineResponse` mid-edit,
the existing split docstring created an orphan string literal. Fixed by rewriting the entire
models file cleanly.

### B4: `isNew` unused variable in FormPage (RESOLVED)
ESLint caught `isNew` was assigned but never used. Removed the variable — `isFromDelivery` and
`isEdit` booleans are sufficient for all branching in the form.
