**Date:** 2026-06-01
**Session Type:** Feature implementation (backend + frontend)
**Focus Area:** Purchasing + Sales modules — companyCode hardcode removal
**Status:** Implementation complete; Docker restart required before smoke tests

## Session Objective

Company code "1000" was retired; "A001" is now the sole company in production.
All hardcoded `"1000"` / `"DEFAULT"` / `"A001"` defaults were replaced with a
live resolver that calls `GET /api/v1/finance/companies?organization_id=...` and
auto-resolves when exactly one company exists for the org.

- `resolve_company_code(organization_id, explicit, auth_token, _cache)` function
- Resolution order: explicit passthrough → per-request cache hit → HTTP call to finance service
- Returns the sole company code when org has exactly 1; raises HTTPException 400 for 0 or >1;

## Architecture Decisions

**Why resolver in API layer, not service layer:**
- Service layer already has many internal callers; changing all internal calls would be risky
- API layer has access to the `Request` object for Bearer token extraction
- Transition methods (submit, approve, cancel) read `companyCode` from the existing stored document header — no resolver needed for those

**Why `model_copy(update=...)` instead of patching service signatures:**
- Sales services take the full Pydantic payload object; adding a separate `company_code` param would require touching all downstream service calls
- Immutable copy is cleaner and doesn't risk mutation of the original request body

**`raw.get("companyCode", "1000")` fallback in transition service methods:**
- Intentionally left as-is for historical documents that were created with "1000" stored
- These are read-paths for existing persisted data, not create-paths
