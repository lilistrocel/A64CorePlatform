## 2. What We Accomplished

### Backend hardening (deliveries.py — Rule 2)

The `deliveries.py` models file used legacy Pydantic V1-style `class Config` blocks
instead of the project's `_RESPONSE_CONFIG` pattern (ConfigDict with to_camel alias
generator + populate_by_name=True + from_attributes=True). Without this, the API
returned snake_case keys, breaking the frontend camelCase expectations.

**Files modified:**
- `src/modules/sales/models/deliveries.py`
  - Added `ConfigDict`, `to_camel` import
  - Defined `_RESPONSE_CONFIG` (line 37–43 after edit)
  - Replaced both `class Config: from_attributes = True` blocks in
    `DeliveryResponse` and `DeliveryListItem` with `model_config = _RESPONSE_CONFIG`
- `src/modules/sales/api/v1/deliveries.py`
  - Added `response_model_by_alias=True` to all 5 route decorators (GET list, GET detail,
    POST from-so, PATCH, POST transition)

**Smoke verification:** `docker compose restart api` + httpx smoke confirmed
camelCase list item keys: `docEntry, docNumber, organizationId, customerId,
customerName, docDate, actualDeliveryDate, status, totalCogs, baseDocRef,
createdAt, updatedAt`.

### salesApi.ts — Delivery types + functions

### Three new pages

**DeliveriesPage.tsx** (`/sales/deliveries`)
- Filter chips: All / Draft / Open / Cancelled
- Date range filter (dateFrom / dateTo)
- Search input (client-side: docNumber + customerName)
- Table columns: DocNumber, DocDate, Actual Delivery, Customer, Source SO, Status, Total COGS
- Source SO column navigates to SO detail; row click navigates to DN detail
- Pagination

**DeliveryFormPage.tsx** (`/sales/deliveries/new`, `/from-so/:soDocEntry`, `/:docId/edit`)
- Three-mode form: new / from-SO / edit
- From-SO mode: fetches SO via `useSalesOrderV2`, pre-fills customer + open lines
  (openQty = orderedQty - deliveredQty - cancelledQty); user can ship less than openQty
- Lines locked in from-SO mode (readonly itemCode/itemName/uom); warehouseId editable
- Max qty hint column shown in from-SO mode; HTML `max` attribute on quantity input
- Edit mode: loads existing DN via `useDelivery`, only header fields editable
- Submit: `createDeliveryFromSO` or `updateDelivery`
- AttachmentList shown in edit mode only (DN must exist first)
- Zod schema with coerce for numeric fields

**DeliveryDetailPage.tsx** (`/sales/deliveries/:docId`)
- Title: `Delivery Note DN-YYYY-NNNN` + StatusBadge
- Action bar:
  - draft: Edit / Post (DRAFT→OPEN) / Delete
  - open: **Generate AR Invoice** button → `/sales/ar-invoices/from-delivery/:dnDocEntry`
  - open + super_admin: Cancel button (OPEN→CANCELLED)
  - cancelled: read-only
- Info grid: customer, dates, status, total lines, total qty, total COGS, notes
- Lines table (read-only): #, itemCode, itemName, description, qty, uom,
  warehouse, returnedQty (amber badge "X of Y returned" when > 0), unitCost, lineCogs
- Doc-chain card: baseDocRef (source SO) + targetDocRefs (ARI, Returns)
- AttachmentList (docType="DELIVERY")
- Delete confirmation modal — X-only close (no overlay dismiss per project rule)
- NO Audit History button (per feedback_sales_ui_no_audit_history_button.md)

### App.tsx + routes

Added lazy imports + 5 routes:
- `/sales/deliveries` → DeliveriesPage
- `/sales/deliveries/new` → DeliveryFormPage
- `/sales/deliveries/from-so/:soDocEntry` → DeliveryFormPage (from-SO mode)
- `/sales/deliveries/:docId/edit` → DeliveryFormPage (edit mode)
- `/sales/deliveries/:docId` → DeliveryDetailPage

Route order: /new and /from-so/:soDocEntry registered before /:docId to prevent
"new" / "from-so" being matched as docId.

Sidebar `Deliveries` entry at `/sales/deliveries` already existed (line 94).

## 3. Bugs/Issues Discovered

### Issue 1: Backend — legacy class Config blocks (FIXED)

- **Severity:** P0 (blocking camelCase API contract)
- **File:** `src/modules/sales/models/deliveries.py` lines 231, 255
- **Root cause:** T-100.8 agent built the DN backend before the `_RESPONSE_CONFIG`
  pattern was standardised (T-100.9a ar_invoices.py introduced it). The delivery models
  used `class Config: from_attributes = True` without the to_camel alias generator.
- **Fix:** Applied `_RESPONSE_CONFIG` to `DeliveryResponse` and `DeliveryListItem`;
  added `response_model_by_alias=True` to all 5 route decorators.
- **Verification:** Live smoke confirmed camelCase keys.

### Issue 2: SO-2026-0001 fully closed (non-blocking)

- **Severity:** P3 (informational)
- **Detail:** The test SO-2026-0001 is in `closed` status (all lines already delivered
  in prior smoke testing). The from-SO endpoint correctly rejects it with 409
  "SO status is closed". To test the from-SO form, a new OPEN SO is needed.
- **Action:** None — this is correct business behaviour. The from-SO route now
  resolves (was 404 before), ready to use with any OPEN SO.
