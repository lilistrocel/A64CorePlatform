## What We Accomplished

### Architecture decision (Option C, with Viet Anh)
Before any code: investigated where `isStock` should live. Three options on the table:
- **A** — column on the existing finance-side `SaleItemFinanceExt` (MySQL).
- **B** — new ops-side `sale_items` Mongo collection, finance ext becomes overlay-only (proper architecture; 3–4× scope).
- **C** — ship **A** now, file a separate ticket for **B** as Wave 6 prep.

Investigation revealed two relevant facts:
1. The de-facto sale-item master today is `SaleItemFinanceExt`. There is no ops-side SKU catalog — ops calls finance over HTTP for every billing-path lookup.
2. `isStock` is a billing-routing flag, not an inventory flag. Inventory tracking (`inventory_movements`, harvest batches, allocations) is entirely ops-side and discovers stock-vs-service implicitly by whether SO lines carry `inventoryId`. Putting `isStock` on the finance side does **not** couple inventory to finance.

Viet Anh chose **Option C**. Filed **T-201.8b** in BACKLOG.md for the Wave 6 SKU-master extraction so the architectural debt is tracked visibly.

3. **Cache invalidation bug — discovered + fixed.** Toggled Basil to Service on
   SalesItemsPage, navigated to AR Invoices → +New direct-create form, Basil didn't
   appear in the combobox typeahead. Root cause: `react-query.config.ts:33` sets
   `refetchOnMount: false` globally (deliberate, comment explains it's to reduce
   refetches). The `useUpdateSaleItemFinanceExt` mutation invalidates `saleItemFinanceExtKeys.all(orgId)`
   which prefix-matches the filtered cache key — but with `refetchOnMount: false`,
   invalidation only marks queries stale without firing a refetch when no observer is
   active. The combobox was unmounted during the toggle save. Hard-refresh worked,
   confirming cache staleness. Fix: added `refetchType: 'all'` to all three
   SaleItemFinanceExt mutations (update, create, delete) — same pattern T-201.5–.7
   used on the DN mutations. Documented in the hook header.

   **Architectural note for future sessions:** the global `refetchOnMount: false` is a
   real footgun. Every mutation in this codebase that invalidates a list query needs
   `refetchType: 'all'` or the same bug recurs silently. Sweeping the entire codebase
   is out of scope; patch when each surfaces. Worth noting in a future refactor pass.

4. **T-202 discovered during Step 3 verification.** Viet Anh recreated ARI-2026-0004
   from DN-2026-0003 and noticed the totals.gross was 29,000 instead of the expected
   30,450. SO had `tax=1450` correctly; ARI had `tax=0`. The frontend was *honestly
   displaying* what the backend stored — backend had stamped `taxPercent=0` on every
   ARI line despite `taxCodeId="S"` being inherited correctly. **Same class of bug as
   T-100.9a.1**: `_get_tax_percent` in ar_invoice_service.py:167 queried `db["tax_codes"]`
   on ops MongoDB. Ops Mongo `tax_codes` collection has count=0; tax codes live in
   finance MySQL. Lookup always returned `Decimal("0")`.

   Accounting impact: every from-Delivery AND direct-create AR Invoice silently dropped
   VAT from its JE. ARC and SO were unaffected (both trust client-submitted `taxPercent`
   directly; never resolved through `_get_tax_percent`).

   Filed as T-202 (top-level, P0). Dispatched backend-dev-expert with the established
   pattern (HTTP wrapper in `_finance_ext_client.py` + delegate from
   `ar_invoice_service._get_tax_percent`). 4 new test cases. 306/306 sales tests pass.
   Re-verified end-to-end on the live stack: ARI-2026-0004 posted with the correct
   3-leg JE: DR AR 30,450 / CR Revenue 29,000 / CR Output VAT 1,450.

   **Standalone-mode tax correctness** was discussed but **deferred to Wave 6** —
   filed as T-600 gap 2a (2026-06-04). Two options surveyed: (a) ops-side `tax_codes`
   Mongo collection seeded at tenant setup OR (b) snapshot `taxPercent` on every doc
