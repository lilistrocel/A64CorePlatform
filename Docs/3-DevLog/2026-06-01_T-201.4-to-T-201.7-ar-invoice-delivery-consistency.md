## What We Accomplished

### T-201.4 — AR Invoice from-Delivery form pre-fill (parent session, direct)
**Problem:** Form had pre-fill logic only for `isEdit` mode. In `isFromDelivery` mode, every field rendered blank. Submit handler at line 612 also referenced `l.baseDocRef?.lineId` which never existed on the form schema, so even with manual line entry the request would have failed.

**Fix in `frontend/user-portal/src/pages/sales/ARInvoiceFormPage.tsx`:**
- Added `useDelivery(deliveryDocId, orgId)` + `useSalesOrderV2(delivery.baseDocRef.docId, orgId)` to fetch the source documents
- New useEffect to reset the form when both load: customer/companyCode/dateOfSupply from Delivery; currency/exchangeRate/paymentTerms/bpRefNo from SO; lines built per-DN-line with pricing/tax inherited from the matched SO line (by `soLineId` first, itemId fallback)
- Added `deliveryLineId: z.string().nullable().optional()` to the line zod schema for tracking source DN line UUID
- Submit handler maps `data.lines` to `{deliveryLineId, quantity, unitPrice, discountPercent, taxCodeId, costCenterId}` and throws if any line lacks `deliveryLineId`
- Customer combobox `disabled={isFromDelivery}` — locked from source
- Loading guard ("Loading source Delivery…") while source docs fetch
- InfoBanner now reads Delivery `docNumber` and explains the price/tax inheritance

**Decision: lock-set for field editability** based on the question "would editing this break document integrity?":
- **Locked:** Customer (combobox), Company Code, UoM, Item picker (already disabled), "+ Add Line" button (hidden in from-Delivery mode)
- **Editable:** Quantity (partial invoicing), Unit Price (legitimate billing-time adjustments), Discount %, Tax Code, Doc/Invoice/Supply dates, Payment Terms, Currency/FX, BP Ref, Notes/Memo, Description
- LineInput styled-component honored `&:disabled, &[readonly]` with muted background + secondary text

### T-201.5 — Visibility + auto-close on full invoice (dispatched: backend + frontend in parallel)
**Problem:** No UI visibility into per-line invoicing progress. Delivery stayed `OPEN` forever even when fully invoiced. Form pre-fill defaulted qty to delivered (not open-invoice qty), so re-entering after a partial invoice would silently fail backend validation.

**Backend (backend-dev-expert):**
- `DeliveryListItem` gains `open_invoice_qty: Decimal` (camelCase alias `openInvoiceQty`)
- New `_compute_open_invoice_qty(raw)` helper sums `quantity − invoicedQty − creditedQty − cancelledQty` per line
- `list_deliveries()` stops projecting `lines` out (needed for computation; lines aren't serialised since DeliveryListItem has no lines field)
- New `_dn_is_fully_invoiced(dn_raw)` + `_write_dn_audit(...)` helpers in `ar_invoice_service.py`
- `create_ar_invoice_from_delivery` step 6 now reloads DN after the invoicedQty increments; if `status == OPEN AND _dn_is_fully_invoiced(dn) == True`, flips to `CLOSED` with audit action `auto_close_on_full_invoice`
- 19 new tests in `src/modules/sales/tests/test_delivery_invoice_visibility.py`

**Frontend (frontend-dev-expert):**
- `salesApi.ts` — `DeliveryListItem.openInvoiceQty: number` added
- `DeliveryDetailPage` Lines table — two new columns (**Invoiced** indigo badge / muted dash; **Open to Invoice** green badge if fully open, amber if partial, muted if zero)
- `DeliveryDetailPage` action bar — "Generate AR Invoice" button hidden when every line's open qty is zero; grey "Fully Invoiced" chip shown instead
- `DeliveriesPage` — "Open to Invoice" filter chip (maps to `status=open`) + per-row `openInvoiceQty` column with amber/muted badge

**Also fixed (parent session, direct):** the from-Delivery pre-fill bug — qty now defaults to `Math.max(0, quantity − invoicedQty − creditedQty − cancelledQty)`, and lines with zero open qty are filtered out of the pre-fill array.

**Verification:** 90/90 backend tests pass independently. `tsc --noEmit` clean. API container restarted, health 200.

### T-201.6 — Counter reconciliation on update / delete / cancel (dispatched backend-dev-expert)
**Problem surfaced by Viet Anh:** "If I delete or edit the draft, the amount tracked won't change right?"

Investigation confirmed two real bugs:
1. **Update bug:** `update_ar_invoice` wrote `updates["lines"] = new_lines` wholesale (line 1593) without touching `Delivery.invoicedQty`. Edit DRAFT 60 → 40 left DN counter stale at 60.
2. **Re-open bug:** `delete_ar_invoice` and `OPEN → CANCELLED` released `invoicedQty` correctly but never re-opened a DN that had been auto-closed by T-201.5 logic. DN stayed CLOSED with `open_invoice_qty > 0`.

**Fix:**
- `update_ar_invoice` — when payload.lines changes AND ARI is from-Delivery: build old/new DN-line totals, compute deltas, cap-check positive deltas against live `open_invoice_qty`, `$inc` each changed DN line, reload DN, apply symmetric auto-close/auto-reopen. Audit detail records `dnLineDeltas` dict.
- `delete_ar_invoice` and `transition_status OPEN→CANCELLED` — after existing release loops, reload DN; if CLOSED + not fully invoiced, transition to OPEN with audit `auto_reopen_on_invoice_release`.
- Reuses `_dn_is_fully_invoiced` + `_write_dn_audit` from T-201.5 — no duplication.

**Tests:** 10 new in `test_delivery_invoice_visibility.py`. **Verification:** 100/100 pass independently.

### T-201.7 — Clean dangling targetDocRefs on delete (dispatched backend-dev-expert)
**Problem surfaced by Viet Anh:** "I deleted an Invoice, but in the document chain seen in delivery note I still see the deleted entry, which upon click navigate me to an empty AR invoice entry with an error AR invoice not found."

Confirmed: `delete_ar_invoice` released `invoicedQty` (T-201.6) but left `Delivery.targetDocRefs` (header) and `Delivery.lines[].targetDocRefs` populated with the deleted ARI's docId. Same pattern in update — wholesale line replacement created new line UUIDs but never pulled the old ones from DN line refs.

**Fix:**
- `delete_ar_invoice` — `$pull {targetDocRefs: {docId: ari_docEntry}}` on the DN header (one call), then `$pull {lines.$.targetDocRefs: {docId: ari_docEntry}}` per affected DN line. Keyed on `docId` so sibling ARIs on the same DN are untouched.
- `update_ar_invoice` — when payload.lines changes AND ARI is from-Delivery: build `old_ari_lineId → dn_lineId` map, `$pull` stale refs (old UUIDs), `$push` fresh refs (new UUIDs) onto matching DN lines. Header ref unchanged (ARI docEntry is stable).

**Tests:** 6 new (1 sanity + 5 main); fake-DB helper extended to handle `$pull` on header arrays and `lines.$.subfield` arrays. **Verification:** 106/106 pass independently.

### Design discussion — direct-create AR Invoice + service-line chain
Viet Anh asked: "if delivery note tracks which warehouse the stock came from, how would we track which warehouse the stock came from when creating AR invoice and skipping all the previous step?"

Confirmed by reading `create_ar_invoice` (line 930) and `transition_status` (DRAFT → OPEN, line 2034): direct-create AR Invoice emits only `sales_invoice_posted` (revenue side). No inventory movement, no COGS event. This means **direct-invoicing a stock item creates a real accounting asymmetry**: revenue without COGS, inventory unchanged, P&L overstates margin.

After comparing three resolution options (item-type gating, SAP B1 "AR Invoice + Delivery" combined, disable direct-create entirely), Viet Anh chose:
- **Option A** — `isStock` flag on sale items; backend rejects stock items in direct-create
- **Way 2** — service-line invoices chain back via the SO (not the DN); the SO becomes the universal billing authorization document
- All ad-hoc fees (late payment, delivery surcharge, monthly retainer, consulting) go through a service-only SO. Every AR Invoice has a chain root.

Filed as T-201.8 → T-201.11 epic.
