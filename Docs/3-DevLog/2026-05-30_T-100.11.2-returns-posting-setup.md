## 1. Session Header

**Objective:** Fix `return_posted` and `credit_note_posted` finance outbox events failing with  
`HTTP 400: Company posting setup not configured for A001`. Ensure end-to-end JE posting works  
for the full returns cycle.

---

## 2. What We Accomplished

### Root Cause Identified

All Wave 3 sales-module outbox events (`delivery_posted`, `sales_invoice_posted`,
`customer_payment_received`, `return_posted`, `credit_note_posted`) emit `companyCode: "A001"`.

The finance DB only had a `company_codes` / `fiscal_periods` / `company_posting_setup` row for
`companyCode: "1000"`.  `_resolve_posting_setup_or_raise` returned HTTP 400 for every A001 event
before even reaching the return-specific or credit-note-specific logic.

**Not a code defect** — the handlers were correctly written in T-100.11.  Pure configuration gap.

**Evidence from live DB:**
```
finance_outbox (failed):
  - delivery_posted      companyCode=A001  error=HTTP 400: ...not configured for A001
  - sales_invoice_posted companyCode=A001  error=HTTP 400: ...not configured for A001
  - return_posted        companyCode=A001  error=HTTP 400: ...not configured for A001
  - credit_note_posted   companyCode=A001  error=HTTP 400: ...not configured for A001

company_codes: only row = companyCode=1000
fiscal_periods: only row = companyCode=1000, fiscalYear=2026
company_posting_setup: only row = companyCode=1000 (arControlAccountId=NULL)
```

### Fix Applied

Created Alembic migration `018_seed_a001_company_posting_setup.py` with 3 idempotent inserts:

1. **`company_codes` row** — A001, org `00000000-0000-0000-0000-000000000001`, "A64 Farm Operations LLC"
2. **`fiscal_periods` row** — A001, 2026-01-01 to 2026-12-31, status=open
3. **`company_posting_setup` row** — A001 with all 10 clearing-account FKs populated:

| Field | Account# | Account Name |
|-------|----------|--------------|
| apControlAccountId | 221000-001 | Trade Payables - Suppliers |
| arControlAccountId | 124000-001 | Trade Receivables - Customers |
| bankAccountId | 126000-002 | Cash at Bank - AED Operating |
| cashAccountId | 126000-001 | Petty Cash |
| grIrClearingAccountId | 223000-004 | Goods Received Not Invoiced |
| inputVatAccountId | 122000-001 | Input VAT Recoverable |
| outputVatAccountId | 222000-001 | Output VAT Payable |
| retainedEarningsAccountId | 312000-001 | Retained Earnings - Prior Years |
| purchasePriceVarianceAccountId | 514000-004 | Purchase Price Variance |
| roundingAccountId | 123000-004 | Advances to Suppliers |

Key decision: `arControlAccountId` is explicitly set to `124000-001` on A001 (it was NULL on 1000).
This makes the setup tier of the 3-tier AR resolution chain self-documenting and removes the
dependency on the hardcoded fallback in `_resolve_ar_control_account_or_raise`.

  a64-finance:/app/alembic/versions/

# INFO: Running upgrade 017 -> 018

## 3. Bugs/Issues Discovered

None — this was a pure configuration gap.  Handler code was correct.

**Schema analysis:** No new columns needed on `company_posting_setup`.  The table already has all
required fields for return and credit-note flows:
- `return_posted` uses inventory/COGS accounts from `sale_item_finance_ext` and `purchase_item_finance_ext` (per-item) — no setup columns needed
- `credit_note_posted` uses `outputVatAccountId` (from setup) + AR via 3-tier chain — both already present
