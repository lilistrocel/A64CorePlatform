**T-200.21 — Foundation enum retrofit** (commit `4bb601d`)
- Replaced 63 ad-hoc TitleCase status literals across purchasing services (`document_service.py` mostly) with the shared `DocumentStatus` enum from `src/core/documents/document_status.py`. Behavior-preserving. Same enum sales has used since Wave 3.
- Vocabulary mapping: `"Draft" → DRAFT`, `"Pending Approval" → PENDING_APPROVAL`, **`"Approved" → OPEN`** (the load-bearing semantic rename — an approved PR/PO in the shared vocabulary is "open"), `"Closed" → CLOSED`, `"Cancelled" → CANCELLED`.
- Migration approach: tolerant `_parse_status(raw)` parser at the top of `document_service.py` accepts BOTH legacy TitleCase strings AND new lowercase_snake enum values. Reads from Mongo go through it; writes always use the new enum-`.value` form. Migration window safety net.
- Migration script: `scripts/migrations/wave4_purchasing_status_migration.py` — idempotent one-shot Mongo migration walking `document_headers` for docType PR/PO/GR/AP and converting the `status` field. **Required deployment step** after the api container is rebuilt.
- Legacy states with no shared-enum equivalent: `"Rejected"`, `"Sent"`, `"Partially Received"`, `"Received"`. Kept as raw strings; routed through `_validate_transition_legacy` table. Whether to add REJECTED / SENT to the shared enum is a future-wave design call.
- Pydantic models: `PRStatus` / `POStatus` / `GRStatus` / `APStatus` changed from `Literal[...]` to plain `str` so Pydantic doesn't reject the new lowercase_snake values against old Literal constraints. Frontend continues to receive a string; UI unchanged.
- Tests: **36 passed / 10 failed** — IDENTICAL to pre-change baseline (verified by stashing + re-running). The 10 failures are pre-existing tech debt filed as **T-200.21a** (commit `5632716`). Sales tests 334 passed (sanity check).

**T-200.22 — Chain reconciler integration** (commit `d4976c3`)
- Applied the `doc_chain_reconciler` pattern from sales to the purchasing PR → PO → GR → AP chain. PO/GR open-qty tracking via shared helper, auto-close when fully consumed downstream, auto-reopen on downstream release, `$pull` dangling targetDocRefs on delete, audit on every chain event. Mirror of what T-201.5/.6/.7 did for sales DN; parameterised via T-201.9.0's refactor.
- **Architectural surprise discovered during the dispatch:** the agent couldn't import the sales `doc_chain_reconciler.py` directly because importing the sales module triggers its `services/__init__.py`, which loads `OrderService` → `redis.asyncio`. Redis is not available in the purchasing test environment — using the import would break 36 previously-passing tests. **Resolution:** wrote a purchasing-specific adapter at `src/modules/purchasing/services/purchasing_chain_reconciler.py` (~820 lines, 13 exports). Same contract as the sales module, adapted to purchasing's schema differences (separate `document_lines` collection vs sales' embedded `lines` array; `docId` instead of `docEntry`; `openQuantity` / `closedQuantity` / `invoicedQty` counters).
- This produces a real architectural concern: **two parallel reconciler modules** that need to stay in sync over time. Filed as **T-200.22a** for future extraction of truly-shared primitives to `src/core/documents/`.
- **Intentional asymmetry vs sales** (documented in code): purchasing PO closes on full receipt, NOT on full invoicing. SAP B1 follows this convention — once goods arrive, the PO is operationally done regardless of when the AP arrives. Sales (T-201.9 bubble-up) uses a different semantic because mixed-SO auto-close needs the rollup.
- **Tax-bug audit performed before dispatch:** purchasing uses `AP_TAX_RATES` hardcoded dict in `models/document.py:495` (`{"S": 5, "SR": 5, "Z": 0, "E": 0, "N": 0}`). Works correctly — no silent 0% bug like sales had pre-T-202. Bad architecture (per-tenant rates need code release) but not a bug. Filed as **T-200.22b** for the HTTP migration.
- Tests: 36 passed / 10 failed (baseline preserved). Sales 334 passed.
