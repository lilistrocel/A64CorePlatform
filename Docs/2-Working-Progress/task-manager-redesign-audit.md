## Why this exists / the vision

The Farm Manager's operational side should be **state-driven and task-driven**:

- A block **generates tasks based on its state**. E.g. when a block is `planned`, a
  "plant the crop" task is generated with **deadline = the planting date** set when the
  virtual block was created; each subsequent state has its own task.
- The **Task Manager** module (Operations tab in the sidebar) is where a manager
  **assigns those tasks to farmer accounts**. Farmers change block state from the field
  via **their own portal** as they complete work.
- The **manual state buttons on the block/virtual card** (e.g. → Growing, → Harvesting,
  → Cleaning, → Empty) act as a **manager override**: pressing one flips the state AND
  should **complete the corresponding task** in the task manager in parallel.

The user has stated this module **must be substantially redesigned**. The audit below
captures what already exists so we build on it rather than rebuild.

## AUDIT — what exists today (2026-06-29)

### Backend — surprisingly mature (mostly complete)

- **Model:** `src/modules/farm_manager/models/farm_task.py`, collection `farm_tasks`.
  Fields: `taskType` (planting, fruiting_check, harvest_readiness, daily_harvest,
  harvest_completion, cleaning, custom), `status` (pending/in_progress/completed/cancelled),
  `priority`, `scheduledDate`/`dueDate`, `assignedTo`, completion fields, `isAutoGenerated`,
  `generatedFromCycleId`, and **`triggerStateChange`** (the state a task flips the block to
  on completion). Daily-harvest has nested `harvestEntries` + grade breakdown. Enriched
  `FarmTaskWithDetails` joins block/farm context.
- **Generation:** `services/task/task_generator.py` — **already implements the core vision.**
  `generate_tasks_for_transition(from_state → to_state)` fires on block state changes and
  creates tasks with **deadlines computed from `block.expectedStatusChanges`** (derived from
  planting date + growth cycle). EMPTY→PLANNED = planting task on the planting date;
  →GROWING/FRUITING/HARVESTING/CLEANING each generate their tasks; daily-harvest spawns one
  task/day; `reschedule_tasks_for_timeline_change` shifts pending tasks; `cancel_future_...`
  cancels on early harvest. Fruiting task only when the plant has a fruiting stage.
- **Repository/Service:** `services/task/task_repository.py`, `task_service.py` — full CRUD,
  list by farm/block/user, `get_my_tasks`, pending count, complete, add harvest entry,
  nightly `aggregate_daily_harvest` (→ creates `BlockHarvest` + updates KPI), bulk
  reschedule/cancel by cycle, assignment validation via `farmer_assignments`.
- **Lifecycle wiring:** `block_service_new.py` — state change → generates tasks;
  harvesting→cleaning auto-completes harvest tasks; **Phase 2 link exists**: completing a
  task with `triggerStateChange` + `triggerTransition=true` calls `BlockService.change_status()`.
- **Daily harvest:** nightly aggregation (~23:00 cron via HarvestAggregatorService) rolls
  entries into a BlockHarvest, updates KPI, spawns next day's task.
- **API:** `api/v1/tasks.py`, ~15 endpoints under `/v1/farm/tasks` — list by farm/block/user,
  `/my-tasks`, `/pending-count`, create custom (`farm.manage`), update, complete, harvest,
  end-harvest, cancel, delete, admin aggregation. Farmers can view/complete; managers gate.
- **Assignment:** `assignedTo` + `farmer_assignments` collection; auto-tasks (assignedTo=null)
  visible farm-wide, custom tasks to the assignee.

### Frontend — minimal MVP, mobile-first

- **Operations flow** (`src/pages/operations/`): `OperationsDashboard` (pick farm, task-count
  cards) → `FarmBlocksView` (pick block) → `BlockTaskList` (the actual task UI).
  **No standalone "Task Manager" page** — it's nested per block. Sidebar "Operations → Task
  Manager" → `/operations` (`MainLayout.tsx` ~300; routes `App.tsx` ~347-349).
- **Works:** task list with Pending/Done status tabs, task cards (type icon, dates, overdue
  flag, assignee *name* display), `TaskCompletionModal` (has "Complete & Transition" when
  `triggerStateChange` set), `HarvestEntryModal`, `ReportAlertModal`.
- **Data layer:** `src/types/tasks.ts`, `src/services/tasksApi.ts` (base `/v1/farm/tasks`,
  covers all endpoints incl. unused `getMyTasks`). No dedicated task hooks — pages call the
  API service directly.
- **Stubbed / MISSING:**
  - ❌ **No assignment UI** — `assignedTo` is display-only; no user/farmer picker.
  - ❌ **`/my-tasks` client method exists but no page uses it** — no per-farmer "my tasks" portal.
  - ❌ **No task-creation form** (createTask endpoint exists, no UI).
  - ❌ Filtering is status-only (no type/assignee/date); no search.
  - ❌ `PendingTasksWarningModal` exists but not wired; photo upload is a placeholder.

### Vision vs. current state

| Vision element | Status |
|---|---|
| Blocks generate tasks from state (planned → planting task, deadline = planting date) | ✅ **Built** (task_generator + expectedStatusChanges) |
| Task Manager assigns tasks to farmer accounts | ⚠️ **Backend ready** (assignedTo, farmer_assignments, /my-tasks); **no assignment UI, no farmer portal page** |
| Manager card buttons flip state **and** complete the matching task | ⚠️ **Half there** — task-completion→state-change exists (`triggerStateChange`); the reverse (flip state → auto-complete matching task) is **not wired** |

**Net:** the engine (state→task generation, lifecycle, daily harvest) is real and working.
The redesign is **mostly frontend + assignment/farmer-portal + wiring the manager buttons
to their tasks** — not a from-scratch rebuild.

## Redesign starting points / open questions (to decide when we resume)

1. **Target Task Manager UX** — a proper standalone surface: manager overview (all tasks,
   filters by type/assignee/status/date/block/farm), assignment UI (user picker), a
   farmer-facing "My Tasks" portal view (wire the existing `/my-tasks`).
2. **Manager-button ↔ task linkage** — when a manager flips a block state via a card button,
   auto-complete the corresponding open task for that transition (the missing reverse of the
   existing `triggerStateChange`).
3. **Farmer portal** — is it the same app with role-gated `/my-tasks`, or a separate portal?
4. **Assignment model** — single assignee today; do we need multi-assignee / team / role-based?
5. **Gaps worth scoping:** notifications/reminders, task-creation UI, editable harvest entries,
   configurable harvest window (currently hardcoded 30 days in task_generator), audit trail.
